# ADR-0004: Custom vendored fork-accurate opcode table

- **Status:** Accepted
- **Date:** 2026-10-28
- **Governs:** design-document §6.1, §6.2, §6.3, §8.2, §14.1, §23.1, §23.4, §27, Appendix B

## Context

The whole product rests on one primitive: deciding, for a given byte offset in
a given contract, what opcode it is, how many immediate bytes follow, and
whether that opcode exists at all in the target EVM fork. §6.1 calls the
handling of `PUSH1`–`PUSH32` immediate data a "critical implementation detail",
and §14.1 makes "Opcode table mapping by EVM version" and "PUSH1–PUSH32
immediate parsing" the first two unit-test requirements.

§23.1 originally said the disassembly layer should be "A maintained EVM
opcode/disassembly library compatible with the chosen EVM fork, wrapped behind
an internal interface", with the warning: "Do not hand-roll opcode definitions
without exhaustive fixtures." §21 question 3 asks which disassembler libraries
are acceptable. §27 item 5 asks the team to record "EVM disassembler library
and supported fork/opcode table".

The candidate libraries were evaluated against that question:

- **`pyevmasm`** — rejected. Its opcode table is stale: it predates `PUSH0`
  (EIP-3855, Shanghai), `MCOPY` (EIP-5656, Cancun), `TLOAD`/`TSTORE`
  (EIP-1153, Cancun), and other modern opcodes. A scanner that silently
  mis-decodes modern bytecode produces wrong findings with high confidence,
  which is the single worst failure mode for this product.
- **`evm-opcodes`** (npm) — Yellow-Paper derived, covers the classic opcode set
  well, but also predates the modern opcodes.
- **`@ethereumjs/evm`** — carries the EIP-5450 stack-effect metadata including
  the modern opcodes, but exposes no clean per-fork opcode-availability table.
- **`ethereum/execution-specs`** — the authoritative source for which opcode
  bytes exist in which fork, with canonical names. It is a Python source tree,
  not an installable library.

Using a stale library means a fork-aware scanner that is not fork-aware.

## Decision

CyberStratum uses a **custom Python analysis package**,
`packages/evm_analysis` (imported as `evm_analysis`), whose opcode table is a
**vendored, generated, versioned artifact**:
`packages/evm_analysis/data/opcodes.json`.

The table is generated by `scripts/generate_opcodes.mjs` from:

- **`ethereum/execution-specs` pinned to tag `v2.20.0`** — for per-fork opcode
  *availability* and canonical names. Each fork's set is read independently from
  `src/ethereum/forks/<fork>/vm/instructions/__init__.py` rather than assuming
  cumulative inheritance.
- **`evm-opcodes`** (Yellow-Paper derived) — for legacy stack effects.
- **`@ethereumjs/evm`** — for modern (EIP-5450) stack effects, including
  `PUSH0`, `MCOPY`, `TLOAD`, `TSTORE`.

Key properties:

1. **Pinned source.** `SPECS_REF = 'v2.20.0'` is hard-coded in the generator.
   Regenerating on a different tag is a deliberate, reviewable act.
2. **Committed artifact.** `opcodes.json` is committed to the repository, so
   the Python engine has **no Node dependency at runtime** and the table is
   diffable and reviewable in code review.
3. **Fail-loud generation.** The generator refuses to emit a table if the
   sources disagree on a stack effect, if a fork loses an opcode relative to its
   predecessor, if `0xFE` (the designated invalid opcode) appears as a valid
   instruction, or if any known opcode lacks a stack effect. It also
   spot-checks specific values (e.g. `SSTORE` = 2/0, `PUSH0` = 0/1,
   `MCOPY` = 3/0, `RETURN` = 2/0) and specific fork introductions (`PUSH0`
   from Shanghai, `MCOPY` from Cancun, `REVERT` from Byzantium, `SHL` from
   Constantinople).
4. **Strict loading.** `evm_analysis.opcodes.load_fork()` raises on an unknown
   fork, a malformed entry, or a duplicate opcode code. It never silently
   degrades: a wrong opcode table would corrupt every downstream finding.
5. **Versioned and reportable.** The artifact carries `schemaVersion`, the
   `sources` provenance string, and the fork list. The provenance string is
   what gets recorded on every scan, satisfying §15's "every scan stores
   parser/rules/model/feature versions".

The engine is structured so that the table is an implementation detail behind
an interface (`load_fork(fork) -> ForkTable`), which is what §23.1 asked for:
if a better library appears later, only `opcodes.py` changes.

### Fork coverage

The vendored table covers fourteen forks in chronological order:

`frontier`, `homestead`, `tangerine_whistle`, `spurious_dragon`, `byzantium`,
`constantinople`, `petersburg`, `istanbul`, `berlin`, `london`, `paris`,
`shanghai`, `cancun`, `prague`.

`petersburg` has no directory in execution-specs — it differed from
Constantinople only by reverting EIP-1283 (net gas metering), which changes gas
costs and not the opcode set — so the generator maps it to `constantinople`
explicitly via `FORK_SOURCE_OVERRIDES`.

## Consequences

**Positive**

- Fork accuracy is a property of the build, not of a library's release cadence.
  `PUSH0`, `MCOPY`, `TLOAD`, and `TSTORE` are all correctly available or
  absent per fork.
- The table is reproducible, diffable, and reviewable; a change in opcode
  semantics shows up as a diff in a committed JSON file.
- The Python engine has no Node runtime dependency; the committed artifact
  means the generator is a build-time tool, not a runtime one.
- Fork-unaware decoding is impossible to do silently: an opcode that does not
  exist in the target fork is reported as `unknown_opcode` with a warning
  rather than decoded as something else.
- The generator's own validation is a second line of defence on top of the
  unit tests.

**Negative / accepted cost**

- We now own the correctness of the table. The cost is bounded by the
  generator's validation rules, the spot-checks, and the unit tests in
  `tests/unit/test_opcodes.py`, but it is a real ongoing obligation.
- The `execution-specs` `Ops` enum is parsed with a regex rather than by
  importing the Python module. That is deliberate (it avoids a Python-side
  dependency on the specs tree at generation time) but it means the parser is
  only as robust as the enum format, which is why the generator enforces a
  minimum opcode count per fork and validates `PUSH1` explicitly.
- `osaka` is **not** in the table. `apps/api/app/core/config.py` currently
  permits `osaka` as a `DEFAULT_EVM_FORK` value; that value is rejected by
  `load_fork()` at analysis time. This inconsistency is tracked and should be
  resolved by either extending the generator's fork list or removing `osaka`
  from the config validator.

**Explicitly not decided here**

- How real-world bytecode is validated against this table. That is
  [ADR-0005](0005-evmole-as-cross-validation-oracle.md).

## Design-document sections resolved

- **§6.1** — the input model is served by a fork-parameterised table; runtime
  and init bytecode are distinguished by the caller, and provenance is
  recorded.
- **§6.2** — tokenization operates on decoded instructions from this table, so
  immediate bytes are never misread as opcodes.
- **§6.3** — block boundaries and `JUMPDEST` discovery are derived from the
  same fork-aware table.
- **§8.2** — the "typed EVM disassembler library" bullet becomes the custom
  `packages/evm_analysis` package.
- **§14.1** — the "opcode table mapping by EVM version" and "PUSH immediate
  parsing" unit-test requirements are satisfied by
  `tests/unit/test_opcodes.py` and `tests/unit/test_disassembler.py`.
- **§23.1** — the "EVM disassembly" row names the custom package and the
  vendored table, and records why `pyevmasm` was rejected.
- **§21** — question 3 ("Which existing disassembler/static-analysis libraries
  are acceptable?") is answered by this ADR and ADR-0005.
- **§27** — item 5 is resolved: the disassembler is the custom package and the
  supported fork/opcode table is the vendored artifact.
- **Appendix B** — ticket 5 ("Implement parser interface and opcode fixture
  tests") is satisfied by `evm_analysis.disassemble` and the unit tests.
